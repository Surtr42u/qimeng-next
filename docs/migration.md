# 原生数据升级、恢复与设备交付

## 哪一种操作适合当前情况

| 想做的事 | 入口 | 写入位置 |
|---|---|---|
| 手机在家中浏览 NAS、拖动进度或编辑标签 | Android 连接 NAS 地址并登录 | NAS 的 Go 服务写入 NAS 本地 SQLite |
| 手机离线收藏或播放自己的文件 | Android 选择本机影库 | 内嵌的同一 Go 服务写入手机私有目录 |
| 将整个 Next 库恢复到一台新机器 | 从「资料备份与归档」下载完整 `.qnext` 和独立 SHA-256，用恢复工具选择新目录 | 新实例获得独立数据根和设备身份 |
| 从旧版 PC v26 整库迁入 Next | [离线转换工具](legacy-cold.md)读取封存数据库、每个库的原件与旧回收站，生成原生归档 | 由同提交的恢复工具写入新目录 |
| 旧手机仅能提供 v2 导出和可核对的原件 | [离线封存已导出事实](mobile-export-recovery.md)，逐件核对旧资产身份、原件和业务记录 | 新建私有来源目录，另存原件与独立摘要，供后续原生投影 |
| 给已有的另一个实例交付部分资料 | 发送端在「资料备份与归档」选择目标和资料，接收端打开「设备领取」 | 接收服务逐项校验后提交本机事务并保存回执 |

## 数据库与现存 Next 数据

SQLite 由运行服务的设备本地持有。升级前先保存完整归档；启动时按顺序执行新增迁移，并核对已执行文件的校验和。遇到未知的新版本或历史文件变化时停止。还原以前的服务版本时，使用该版本对应的归档另起实例。

本轮迁移 0034 将已知版本的续播点移入独立记录；0035 分离资产、不可变原件版本和当前位置；0036 保存设备结果包、来源绑定和逐项回执；0037 给标签分配稳定 ID 并保留显示顺序；0038 将组图页、短剧集的序号写在集合成员上。已有数据有可靠记录时沿用原值。无法证实的历史原件摘要保持未知；冲突或缺失的旧集序留给人工确认。字段所有权、写入接口和重试依据见[架构](architecture.md#next-原生数据与恢复)。

迁移 0039 将现存 Next 集合的别名逐项按原顺序写入独立关系，保留集合 ID、所属库和业务修订。升级前的命名修订沿用同一数值，已有待提交计划据此复核。旧标签从空别名列表开始，已删除词条和旧拼写的墓碑继续生效。升级后，SQLite 检查点会包含这两类别名。[迁移脚本](../server/internal/store/migrations/0039_owner_aliases.sql) · [旧库升级与快照回读](../server/internal/store/aliases_test.go)

迁移 0040 为已有出处与角色关系增加顺序。升级以旧关系表的实际成员为准，从旧数组恢复这些成员首次出现的位置，缺少顺序的列在其后并按稳定 ID 排列。只有文字的记录继续保留原文，已有成员旁的陈旧展示名和无关系佐证的缓存 ID 不会新建关联。旧库没有记录某个已关联出处是否仅由角色带出，升级保留原关系，所有者可以显式解除。新上传和智能计划会冻结原始选择，角色带出的出处始终按当前词表回读。[迁移脚本](../server/internal/store/migrations/0040_asset_taxonomy.sql)

迁移 0041 为已封存且尚未上传的输入保存空文件和不支持后缀的原因。原清单顺序和指纹、已有上传、已取消的输入以及之前签发的回执继续可查。存在新诊断时更新备份检查点的业务修订。已为有效媒体准备的计划继续沿用原来的批次修订。[迁移脚本](../server/internal/store/migrations/0041_intake_rejections.sql)

迁移 0042 为已有的受限任务保留默认关闭的单帧外发权限。完整归档中的研究回执继续使用 `research_provider_calls` 保存所查对象、版本和结果，图片回执另含已发帧 ID 与 SHA-256。回读证据无需再次联网。衍生帧可从原件重建，Lens 地址与密钥由新实例管理员按需配置。[迁移脚本](../server/internal/store/migrations/0042_research_image_lookup.sql)

迁移 0043 为已封存智能清单、活动发布意图与批次凭据增加查询索引。发现接口从现有清单、上传及任务实时判断可认领范围。已有批次、任务凭据、累计预算与操作回执继续沿用原记录。

## 完整归档与隔离恢复

已核验的旧 PC 恢复副本可作为图片校对的基线。所有者提交显式成员计划后，离线命令将合并结果发布到新目录。同一决定在新的整库恢复后可凭业务回执复核，原始完整归档继续保留。[已校对图片的合并与回读](selected-image-merge.md)

迁移 0044 将智能执行器的当前停等观察绑定到原任务、租约代次和实际批次修订。升级前的任务沿用已有认领和授权事实，不补造过往的宿主状态或时间。隔离恢复撤销原执行器能力时，同时移除绑定旧租约的观察，库内作品、输入和提交回执照常恢复。[迁移脚本](../server/internal/store/migrations/0044_intake_executor_status.sql)

归档格式 `qimeng-next-backup` 目前为版本 1。清单绑定来源实例、资产 ID、内容版本、原件大小及 SHA-256，数据库取自同一检查点。服务端只发布已完成且确认摘要的归档。原件发生变化时保留失败原因，可对当前状态新建检查点。

想取回替换前的视频原件时，选择替换前已完成的归档。替换后的归档保存新原件，并在数据库中保留旧版本的摘要、媒体参数和时间轴绑定。两次恢复的逐项比对见[版本与整库恢复验收](verification.md#原生资产的版本与整库恢复)。

1. 从服务端保存 `.qnext` 文件和独立提供的 SHA-256。
2. 执行 `qimeng-backup verify --archive <归档> --sha256 <摘要>`。再执行 `qimeng-backup restore --archive <归档> --sha256 <摘要> --destination <尚不存在的新目录>`。
3. 从新目录启动实例，重新登录。回读原件字节并逐项比对摘要，再核对收藏、作者、标签、历史事件和各自的内容版本。旧时间轴保留原版绑定。外部存储配置和设备凭据需要在新实例重新授权。
4. 出现 `RESTORE_INCOMPLETE` 时保留现场供排查，选择新的空目标重试。切换至恢复后的实例前保留原实例与归档。

## 批次独立保护中断后怎样继续

沿用原操作键重试。服务从这次操作已经发布的 SQLite 快照回读封存清单、上传归属、资产和内容版本，并核对当前原件。假如快照中仅 A 已入库，B 在中断后才完成，原保护只覆盖 A。B 的来源继续保留，等新建的保护快照包含 B 后，再按它的保护编号申请来源回收许可。

在原实例重试升级前的保护、签发许可或回读仍有效的旧许可时，服务补查当时的业务快照。如果仅本地检查点丢失，服务自动从该保护记录指定的独立目标取回快照，核对故障域、卷归属、SHA-256 和字节数，再只读查询封存清单和入库版本。已核实快照缺少对应输入或版本时，新的许可请求会被拒绝，未决旧许可显示为已撤销。本地检查点损坏会中止回查。需要独立副本时，目标不可用或副本不符也会返回核验错误，来源继续保留。

回读旧许可时，服务在查完快照后核对当前执行器、实际入库版本、许可期限和已经登记的去向。等待期间已经登记的回执可直接回读。执行器仍可用原许可编号登记已经发生的实际去向。整库恢复到新实例时，旧回收许可按恢复流程撤销。[批次保护与来源回执](api.md#媒体与备份)

从独立目标回查时，每个实例同时只在私有缓存中暂存一份快照，写入时保留配置的磁盘余量。请求结束或取消后清理暂存文件。进程被强制终止时，下次回查会清理该实例专用位置遗留的快照和 SQLite 辅助文件，再从目标重新核验。

## 选择性设备交付

运输协议版本 2 的 `nativeSelection` 使用独立的 `qimeng-native-selection` 格式版本 1。包标识是原始字节的 SHA-256。每个包写明来源和接收实例，每项携带稳定对象 ID、种类及业务修订。时间轴条目同时绑定两端明确选择的视频 ID、内容版本和原件摘要。读取器拒绝无法解释的版本。手机直接连接 NAS 时，所有日常操作通过 NAS 的正式 API 完成。

发送端从当前服务选择作者 TXT、已确认的作者资料块，或适用于指定视频的标记。接收端先预览本机处置，保留或替换均记录在指纹中。人工修改、清空、同名异人、文件变更或目标已有其他版本时，逐项显示原因。业务变更与成功回执一同提交。应答丢失或同一包经另一个运输任务重发时，接收端按包和对象回读已有结果。发送端读取段摘要及本机回执编号，接收端可查看每一项的决定。[交付接口与保护范围](api.md#显式设备维护包)

接收库从整库归档恢复后，重新配对时填写新接收实例 ID。同一来源实例再次交付同一作者的其他资料块时，服务沿用此前绑定的本地作者 ID，每个块分别核对来源修订、本地修订和回执。为新条目选择目标时，如果历史绑定指向多位本地作者，该项返回 `identity_conflict`，保留各位作者的资料。已绑定的本地作者被删除后，后续资料块也保留这次删除决定。

## 历史记录与旧版 PC 的一次性转换

旧版 qimeng-media 用于核对命名、推荐、收藏、时间轴和明确替换等已确认体验。早期 Next 实例已产生的 v2 导入记录可按管理员权限查阅，其原始资料、处置、来源标识与未知内容版本保持原样。普通服务的旧暂存、建计划和提交写入口返回 HTTP 410。PC v26 整库迁入使用独立的离线转换器，要求一致数据库及明确选择的原件根和旧回收站。每个库、资产与回收项都在新目录恢复；原始操作证据、缺失版本与排除范围记入私有报告。[转换与核对步骤](legacy-cold.md)

手机将来切换成纯客户端前，先在新目录恢复手机独有资料，确认 NAS 上的内容、关联与历史，最后更换安装变体。真实设备、存储挂载和恢复演练各自记录。[本机模块与剥离](runtime-separation.md) · [当前验收](status.md)
