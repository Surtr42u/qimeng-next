# 原生数据升级、恢复与设备交付

## 哪一种操作适合当前情况

| 想做的事 | 入口 | 写入位置 |
|---|---|---|
| 手机在家中浏览 NAS、拖动进度或编辑标签 | Android 连接 NAS 地址并登录 | NAS 的 Go 服务写入 NAS 本地 SQLite |
| 手机离线收藏或播放自己的文件 | Android 选择本机影库 | 内嵌的同一 Go 服务写入手机私有目录 |
| 将整个 Next 库恢复到一台新机器 | 从「资料备份与归档」下载完整 `.qnext` 和独立 SHA-256，用恢复工具选择新目录 | 新实例获得独立数据根和设备身份 |
| 给已有的另一个实例交付部分资料 | 发送端在「资料备份与归档」选择目标和资料，接收端打开「设备领取」 | 接收服务逐项校验后提交本机事务并保存回执 |

## 数据库与现存 Next 数据

SQLite 由运行服务的设备本地持有。升级前先保存完整归档；启动时按顺序执行新增迁移，并核对已执行文件的校验和。遇到未知的新版本或历史文件变化时停止。还原以前的服务版本时，使用该版本对应的归档另起实例。

本轮迁移 0034 将已知版本的续播点移入独立记录；0035 分离资产、不可变原件版本和当前位置；0036 保存设备结果包、来源绑定和逐项回执；0037 给标签分配稳定 ID 并保留显示顺序；0038 将组图页、短剧集的序号写在集合成员上。已有数据有可靠记录时沿用原值。无法证实的历史原件摘要保持未知；冲突或缺失的旧集序留给人工确认。字段所有权、写入接口和重试依据见[架构](architecture.md#next-原生数据与恢复)。

迁移 0039 将现存 Next 集合的别名逐项按原顺序写入独立关系，保留集合 ID、所属库和业务修订。升级前的命名修订沿用同一数值，已有待提交计划据此复核。旧标签从空别名列表开始，已删除词条和旧拼写的墓碑继续生效。升级后，SQLite 检查点会包含这两类别名。[迁移脚本](../server/internal/store/migrations/0039_owner_aliases.sql) · [旧库升级与快照回读](../server/internal/store/aliases_test.go)

迁移 0041 为已封存且尚未上传的输入保存空文件和不支持后缀的原因。原清单顺序和指纹、已有上传、已取消的输入以及之前签发的回执继续可查。存在新诊断时更新备份检查点的业务修订。已为有效媒体准备的计划继续沿用原来的批次修订。[迁移脚本](../server/internal/store/migrations/0041_intake_rejections.sql)

## 完整归档与隔离恢复

归档格式 `qimeng-next-backup` 目前为版本 1。清单绑定来源实例、资产 ID、内容版本、原件大小及 SHA-256，数据库取自同一检查点。服务端只发布已完成且确认摘要的归档。原件发生变化时保留失败原因，可对当前状态新建检查点。

想取回替换前的视频原件时，选择替换前已完成的归档。替换后的归档保存新原件，并在数据库中保留旧版本的摘要、媒体参数和时间轴绑定。两次恢复的逐项比对见[版本与整库恢复验收](verification.md#原生资产的版本与整库恢复)。

1. 从服务端保存 `.qnext` 文件和独立提供的 SHA-256。
2. 执行 `qimeng-backup verify --archive <归档> --sha256 <摘要>`。再执行 `qimeng-backup restore --archive <归档> --sha256 <摘要> --destination <尚不存在的新目录>`。
3. 从新目录启动实例，重新登录。回读原件字节并逐项比对摘要，再核对收藏、作者、标签、历史事件和各自的内容版本。旧时间轴保留原版绑定。外部存储配置和设备凭据需要在新实例重新授权。
4. 出现 `RESTORE_INCOMPLETE` 时保留现场供排查，选择新的空目标重试。切换至恢复后的实例前保留原实例与归档。

## 选择性设备交付

运输协议版本 2 的 `nativeSelection` 使用独立的 `qimeng-native-selection` 格式版本 1。包标识是原始字节的 SHA-256。每个包写明来源和接收实例，每项携带稳定对象 ID、种类及业务修订。时间轴条目同时绑定两端明确选择的视频 ID、内容版本和原件摘要。读取器拒绝无法解释的版本。手机直接连接 NAS 时，所有日常操作通过 NAS 的正式 API 完成。

发送端从当前服务选择作者 TXT、已确认的作者资料块，或适用于指定视频的标记。接收端先预览本机处置，保留或替换均记录在指纹中。人工修改、清空、同名异人、文件变更或目标已有其他版本时，逐项显示原因。业务变更与成功回执一同提交。应答丢失或同一包经另一个运输任务重发时，接收端按包和对象回读已有结果。发送端读取段摘要及本机回执编号，接收端可查看每一项的决定。[交付接口与保护范围](api.md#显式设备维护包)

## 历史记录与将来的一次性导入

旧版 qimeng-media 用于核对命名、推荐、收藏、时间轴和明确替换等已确认体验。Next 单独定义自己的数据协议。已在早期 Next 实例中产生的 v2 导入记录可按管理员权限查阅，其原始资料、处置、来源标识与未知内容版本保持原样。普通服务的旧暂存、建计划和提交写入口已退役。将来确有个人资料需要迁入时，再单独设计一次性工具，并在副本逐项核对身份、原件、人工决定和历史。

手机将来切换成纯客户端前，先在新目录恢复手机独有资料，确认 NAS 上的内容、关联与历史，最后更换安装变体。真实设备、存储挂载和恢复演练各自记录。[本机模块与剥离](runtime-separation.md) · [当前验收](status.md)
